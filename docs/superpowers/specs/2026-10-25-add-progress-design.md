# 레퍼런스 추가 — 단계별 진행률·예상 시간 — 설계

작성일: 2026-10-25. 대상: 로컬 UI 레퍼런스 추가 화면(`#/add`, `scripts/ui/api_add.py`, `pages/add.js`).

## 1. 왜

43분짜리 영상을 넣었더니 "컷" 단계에서 8분 동안 아무 변화가 없었다. 사용자는 이게 정상인지 멈춘 건지 알 수 없었다.

사용자 요구(그대로): 영상은 한 번에 하나씩 넣는다. 단계별로 진행률을 보고 싶고, 예상 완료 시간에 비해 얼마나 왔는지 알고 싶다. 시안: `.superpowers/brainstorm/107174-1792885059/content/add-progress.html`. 사용자 승인됨.

성공 기준: 긴 영상을 넣어도 어느 단계가 몇 %인지, 몇 분 남았는지, 몇 시쯤 끝나는지가 보인다. 예상보다 길어지면 그렇다고 표시된다.

## 2. 범위

목표
- 영상 카드의 단계(자막·컷·분석)마다 진행 막대를 단다. 끝난 단계는 "걸린 시간 (예상 시간)", 진행 중인 단계는 "N% · 경과 / 예상", 다음 단계는 "예상 시간"을 보여 준다.
- 진행 중인 단계 아래에 지금 하는 일을 한 줄로 보여 준다. 예: "영상 받는 중 45%", "장면 확인 중 (38,800 / 62,600 프레임)", "음성 인식 중 12:30 / 43:31". 남은 시간과 예상 완료 시각도 함께 보여 준다.
- 카드 맨 아래에 그 영상 전체의 남은 시간과 예상 완료 시각을 보여 준다.
- 예상을 넘기면 막대를 주황색으로 바꾸고 "예상보다 길어지는 중"이라고 표시한다.
- 이 PC에서 실제로 걸린 시간을 기록해 다음 예상에 쓴다.

샷 분류만 보강(`run_shots_only`)도 포함한다. 그 카드는 "샷" 한 줄만 보이는 같은 단계 줄 UI를 쓰고, 영상 길이는 `fetch.load_raw`로 얻는다. **(제 판단)**

비목표
- 다른 화면(유형화, 모티브, 기획안, 콘티, 자막 영상)의 진행 표시. 이번에는 레퍼런스 추가만 한다. 다른 화면에서 재사용할 수 있게 만드는 것은 좋지만 붙이지는 않는다.
- 여러 영상을 합친 전체 남은 시간. 링크를 여러 개 넣었을 때도 영상 카드마다 따로 보인다.
- 진행이 멈췄을 때 자동으로 중단하는 기능(watchdog). 이번에는 표시만 한다.

안티골(이렇게 되면 실패)
- 진행률이 뒤로 가거나 100%에서 한참 머문다. 측정할 수 없는 구간을 %로 꾸며내지 않는다.
- 진행 표시 때문에 처리가 눈에 띄게 느려진다. 진행 갱신은 0.5초에 한 번 이하로 한다.
- 시간 기록 파일이 깨졌다고 수집이 실패한다. 기록은 보조 정보이므로, 읽기·쓰기가 실패해도 기본값으로 계속한다.
- "확인 필요"(사용자 결정 대기) 시간이 예상 시간에 섞인다.

## 3. 단계와 측정 방법

단계는 지금 화면의 칩과 같다: `fetch`(자막), `cuts`(컷), `analyze`(분석). 샷 분류(`shots`, 선택)도 같은 방식으로 다룬다. 확인 대기(`confirm`, awaiting)는 시간을 재지 않는다.

| 단계 | 하위 구간 | 진행률 근거 | 비고 |
|---|---|---|---|
| 자막 `fetch` | 차단 방지 대기(`fetch.wait_turn`) | 남은 대기 초(정확) | "차단 방지 대기 N초" |
| | 메타·자막 받기 | 측정 불가 | 보통 몇 초 |
| | 음성 인식(STT, 선택했을 때) | 처리한 음성 끝 시각 / 영상 길이(정확) | faster-whisper segments는 순서대로 나온다 |
| 컷 `cuts` | 차단 방지 대기 | 남은 대기 초 | |
| | 영상 받기 | yt-dlp `progress_hooks`의 받은 바이트/전체 바이트 | 전체를 모르면 측정 불가로 둔다 |
| | 장면 감지 | 읽은 프레임 / 전체 프레임 | PySceneDetect `detect()`는 콜백이 없다. 빌더가 SceneManager나 위치 폴링으로 구현한다 |
| | 카메라·대표 프레임 | 처리한 장면 / 전체 장면 | `analyze_video`의 장면 반복문 |
| 분석 `analyze` | Claude 호출 | 측정 불가 | 예상 대비 경과만 보여 준다 |
| 샷 `shots` | Claude 호출 | 측정 불가 | 같은 방식 |

- 단계 진행률은 하위 구간의 가중 합이다. 가중치는 빌더가 이 PC에서 실측해 정한 고정 기본값이다(2026-10-25, 1208초 영상·508장면: 컷 320초 = 받기 약 5초, 장면 감지 약 92초, 카메라 약 225초 → 받기 0.03, 장면 감지 0.30, 카메라 0.67). 하위 구간별 시간을 기록해 가중치를 고치는 것은 나중 일이다. **(제 판단)**
- 마지막 가중 구간(컷의 카메라)은 그 구간의 진행률이 0.1 이상이면, 단계 전체 진행률 대신 그 구간이 시작된 뒤 걸린 시간과 그 구간의 진행률로 남은 시간을 계산한다(가중치 오차가 남은 시간에 섞이지 않게). 서버는 `phase_started_at`(구간이 바뀐 시각)과 `phase_fraction`(그 구간 자체의 0~1)을 함께 보낸다.
- 측정할 수 없는 구간은 진행률을 `null`로 두고, 화면은 그 단계를 "경과 / 예상" 막대로 보여 준다. 막대는 경과/예상 비율이고 100%에서 멈춘다.
- 진행률은 줄어들지 않는다. 하위 구간이 바뀔 때도 이전 값보다 작으면 이전 값을 유지한다.

## 4. 예상 시간

- 예상 시간의 기준은 단계마다 다르다. **(제 판단)**
  - 컷, 음성 인식(STT): 영상 길이 × 이 PC의 속도(걸린 시간/영상 길이) + 고정 몫.
  - 자막 받기(STT 없이): 길이와 무관한 최근 기록의 중앙값.
  - 분석·샷: Claude 호출이라 길이에 덜 비례한다. 기록에 첨부 프레임 수와 대본 글자 수도 함께 남기고, 기본은 최근 기록의 중앙값을 쓴다. 기록이 충분하면(5건 이상) 프레임 수·글자 수로 보정해도 된다(빌더 재량).
- 영상 길이: 캐시된 raw가 있으면 `fetch.load_raw`, `no_transcript` 오류면 `details.duration_sec`, 그 밖에는 `fetch` 결과의 메타 `duration`에서 얻는다. 메타에 길이가 없으면 컷 통계의 `duration_sec`를 받은 뒤부터 쓴다. 길이를 모르는 동안에는 길이에 비례하는 단계의 예상을 "예상 계산 중"으로 보여 준다.
- 기록: `workspace/timings.json`. 단계마다 최근 20건의 `{video_sec, elapsed_sec, at}`. 분석·샷은 엔진(`llm.config()["engine"]`)별로 나눈다. **(제 판단)**
  - 쓰기는 단계가 정상으로 끝났을 때만 한다(실패·취소·캐시 사용은 기록하지 않는다).
  - 자막 단계는 두 기록으로 나눈다: `fetch`(메타·자막 받기)와 `stt`(음성 인식). 사이의 사용자 결정 대기는 어느 쪽에도 넣지 않는다. 화면에서는 둘 다 "자막" 줄에 합쳐 보인다. **(제 판단)**
  - 재분석(확인 뒤 "다시 분석"): 분석 줄을 새로 시작한다(`started_at` 갱신, 경과 0부터). 끝나면 그 회차도 정상 완료로 기록한다. 확인 대기 뒤의 재분석 시간은 카드의 "전체 남은 시간"에 미리 더하지 않는다. **(제 판단)**
  - 기록이 깨졌거나 쓰지 못하면 조용히 기본값을 쓴다(안티골).
- 속도 추정: 최근 기록의 초/영상초 비율의 중앙값. 기록이 3건 미만이면 기본값과 섞는다(빌더 재량). **(제 판단)**
- 기본값(기록 없을 때)은 빌더가 이 PC에서 실측해 정하고 상수로 둔다. 참고 실측(2026-10-25, 43분 31초 영상): 컷 약 8분, 분석은 길이에 덜 비례.
- 캐시를 쓰는 단계(이미 있는 컷 통계 등)는 바로 끝나므로 예상을 0으로 보여 준다.

## 5. 서버 → 화면 데이터

작업 항목(`jobs.new_item`의 dict)에 필드 하나를 더한다. **(제 판단)**

```json
"timing": {
  "video_sec": 2611.1,
  "steps": {
    "fetch":   {"state": "done",    "elapsed": 38.2, "expected": 40.0},
    "cuts":    {"state": "running", "started_at": 1792900000.1, "expected": 490.0,
                "fraction": 0.62, "phase": "scenes", "phase_text": "장면 확인 중 (38,800 / 62,600 프레임)"},
    "analyze": {"state": "pending", "expected": 150.0}
  }
}
```
- `started_at`은 서버 시각(epoch 초)이다. 화면은 폴링 사이에도 시계를 1초마다 움직인다. 서버와 브라우저의 시계 차이는 `Job.snapshot()` 최상위에 새로 넣는 서버 현재 시각 `now`로 보정한다. 다른 kind의 스냅샷에도 `now`가 붙지만 무해하다. **(제 판단)**
- `fraction`은 0~1 또는 `null`(측정 불가)이다. `phase_started_at`(지금 하위 구간이 시작된 서버 시각, 일시정지 시간만큼 `started_at`과 함께 밀린다)과 `phase_fraction`(그 구간 자체의 0~1)도 보낸다.
- 같은 줄을 다른 기록 이름으로 다시 시작하면(자막 줄: 메타·자막 받기 → 음성 인식) 앞 회차의 걸린 시간을 `prior_elapsed`로 남긴다. 화면의 "✓ … 걸림"은 `prior_elapsed + elapsed`를 보여 주고, 기록(`fetch`, `stt`)은 따로 남는다.
- 줄 상태 `state`는 다섯 가지다.
  - `pending`: 아직 시작하지 않음.
  - `running`: 진행 중. `paused_at`이 있으면 사용자 결정 대기나 차단 방지 대기로 시계가 멈춘 상태다.
  - `done`: 정상 완료. 캐시를 썼으면 `expected` 0.
  - `failed`: 오류로 끝남. 기록하지 않는다.
  - `skipped`: 오류가 아니라 하지 않음. STT를 쓸 수 없어 화면 분석으로 갔거나, 프레임이 없어 샷을 건너뛰었거나, 항목이 먼저 끝나 시작하지 않은 줄이다. `expected` 0, 기록하지 않는다.
  - 항목이 끝나면(저장·건너뜀·이미 있음·실패) `pending`으로 남은 줄은 `skipped`가 된다. 끝난 카드에는 남은 시간이 보이지 않는다.
- 확인 대기(awaiting)에 들어가면 그 시간은 어떤 단계에도 넣지 않는다.
- 갱신은 `job.update`를 쓰되 0.5초에 한 번 이하로 한다(안티골). 스냅샷 크기는 작게 유지한다.

## 6. 화면(시안 그대로)

- 영상 카드의 지금 단계 칩 자리를 단계 줄 목록으로 바꾼다. 줄마다 이름, 막대, 오른쪽 글자가 들어간다.
  - 끝난 줄: "✓ 0:38 걸림 (예상 0:40)"
  - 진행 중인 줄: "62% · 5:02 / 예상 8:10". 측정 불가면 "5:02 / 예상 8:10"
  - 다음 줄: "예상 2:30"
- 진행 중인 줄 아래 한 줄: `phase_text` · "약 3분 남음" · "11:16쯤 끝".
- 카드 맨 아래: "이 영상 전체: 약 5분 30초 남음 · 예상 완료 11:19".
- 예상을 넘기면 막대가 주황색이고 '예상보다 길어지는 중'이 붙는다. 측정 진행률이 0.1 이상이면 그 진행률로 남은 시간을 계속 보여 주고, 측정 불가 구간만 남은 시간을 '곧 끝날 예정'으로 바꾼다. 음수는 보여 주지 않는다.
- 확인 대기 중이면 시간 표시를 멈추고 "확인을 기다리는 중"을 보여 준다.
- 시간 형식은 `m:ss`, 1시간 이상이면 `h:mm:ss`, 시각은 `HH:MM`.
- 색은 기존 토큰을 쓴다(진행 `--accent`, 완료 `--ok`, 초과는 기존 경고색). 새 색 토큰은 만들지 않는다.
- 진행 막대는 `role="progressbar"`와 `aria-valuenow`를 쓴다. 측정 불가일 때는 `aria-valuenow`를 빼고 `aria-valuetext`로 "5분 2초 경과, 예상 8분 10초"를 준다. 1초마다 움직이는 숫자는 `aria-live`로 읽지 않는다.

## 7. 테스트와 완료 조건

- 단위: 예상 계산(기록 없음/1건/여러 건, 엔진별), 기록 파일이 깨졌을 때 기본값, 진행률이 줄지 않음, 가중 합, awaiting 시간 제외.
- 단위: STT 진행(가짜 segments), 받기 진행(가짜 progress_hooks 값, total 없음), 장면 감지·카메라 진행 콜백 호출.
- API: 수집 작업 스냅샷에 `timing`이 있고 단계 상태가 차례로 바뀐다(가짜 fetch/cuts/llm). 갱신 빈도 제한.
- 화면: 순수 함수(시간 형식, 남은 시간·완료 시각, 초과 판정)를 node로 테스트한다(`help-utils.js`처럼 import 없는 모듈).
- 실제 확인(완료 조건): 실제 10분 이상 영상 하나를 넣는다.
  - 컷 단계 막대가 받기 → 장면 → 카메라 순서로 차오르고, 줄어들지 않는다.
  - 분석 단계가 경과/예상으로 보이고, 끝나면 `workspace/timings.json`에 기록이 남는다.
  - 두 번째 영상의 예상이 첫 기록을 반영한다.
- 문서: README의 레퍼런스 추가 설명에 한 줄 추가, `docs/help/add.md`의 "이렇게 나와요"·"알아 둘 것" 갱신(도움말 브랜치가 main에 들어간 뒤), PLAN.md Phase 추가, 설계서 v2 해당 절.

## 8. 빌더에게 맡기는 것
- 장면 감지 진행을 얻는 구체 방법(SceneManager 콜백, 별도 스레드에서 위치 읽기 등). 처리 속도를 떨어뜨리지 않는 쪽.
- 하위 구간 기본 가중치와 기본 속도 상수(실측해서).
- 중앙값 계산에 쓰는 기록 수, 기본값과 섞는 방식.
- 단계 줄 CSS 세부.
